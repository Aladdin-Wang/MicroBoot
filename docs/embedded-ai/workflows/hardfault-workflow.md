# 程序进异常，先把出错现场留下来

程序突然没反应，先别急着复位。异常寄存器和堆栈还在时，更容易找到出错位置。

> 程序进异常了，先保存现场，找到对应代码，看看是什么原因。

## AI 要拿到什么

提供当前工程以及与板上固件匹配的 AXF/ELF。AI 会结合异常状态、堆栈和源码分析，给出出错位置、支持判断的数据，以及还不能确定的部分。

![HardFault 现场与源码定位](../../images/mklink/cases/stm32f103-rt-thread/stm32-hardfault-source.png)

## 在网页里怎么看

Cortex-M 工程打开 **仪表盘 → HardFault**，点击检查，查看异常原因和源码位置。函数名、调用路径和寄存器状态要能相互对应；只出现一个栈扫描候选函数，还不能认定它就是根因。

> 这个位置为什么会出错？结合调用参数和内存访问再检查一下。

RTOS 工程的异常入口可能额外保存寄存器。自动定位不合理时，让 AI 核对异常栈，而不是照着第一个函数名修改。

## HPM 使用另一套异常信息

HPM 是 RISC-V，发生 Trap 时要看对应的异常原因和指令地址。工程应保留可读取的 Trap 现场，再用当前 ELF 定位源码。操作说明见 [HardFault / RISC-V Trap](../../mklink/debugging/hardfault.md)。

## 修改后再确认一次

> 修复后重新编译下载，按刚才的触发条件复测，看看任务能否继续运行。

复位能让程序重新开始，修复还需要同样条件下的验证。日常排查无需额外加入故障注入代码。
